# Working on the Brand Butlers app

- The whole app is `app/index.html` (one self-contained page). Icons and manifest sit next to it.
- `dev` = test version at https://9kpkwdd79f-web.github.io/Brand-Butlers-app/preview/
- `main` = live app at https://9kpkwdd79f-web.github.io/Brand-Butlers-app/
- Every change goes to `dev` first. Only merge `dev` into `main` when the user says to deploy, and add a line to `CHANGELOG.md` with the release.
- Pushes from Claude sessions do not trigger the workflow by themselves. After pushing, start it with
  `POST /repos/9kpkwdd79f-web/Brand-Butlers-app/actions/workflows/deploy.yml/dispatches {"ref":"main"}` (only `main` may publish; keep `.github/workflows/deploy.yml` the same on both branches)
  (one run publishes both branches) and wait for it to finish before reporting.
- The deploy script stamps `const BUILD = '__BUILD__'` in each copy with that branch's commit; open apps compare it with the published page and show "New version available". Keep that line in `app/index.html`.
- Desktop layout: admins on screens 1024 px and wider get `body.desk` (sidebar, Overview dashboard with table + side panel, Approvals list + report panel). Built in the DESKTOP LAYOUT block (`isDesk`, `renderSide`, `overviewDesk`, `approvalsDesk`, `deskPanel`). Round 2 (desktop only): New ticket in two columns with a live summary (`newDesk`, `ntSummary`), Insights with charts (`insightsDesk`, country colours `--c0..--c3`), library grid with search/filters/drag-and-drop/hover preview (`videosDesk`, `pickFiles`), and a big-screen video editor (draggable clip edges, clip list, keyboard shortcuts). Phones and the installer view are unchanged; keep desktop-only styling under `body.desk` / desktop functions.
- Privacy by design is a standing rule for all code: read and follow `docs/privacy.md`. Passwords are hashed with SHA-256 in the browser (`pwHash`/`signInHashed`) before they reach Supabase (which bcrypts them); old readable passwords are moved over on the next sign-in. Libraries are self-hosted in `app/vendor/` (no CDNs).
- Never put NaaUt on the report. Client is always Apple.
- Apple export: when an admin approves, the app makes the client's "Reactive maintenance - statement of completion" PDF in the browser (`buildPdf`, jsPDF 2.5.1 from `app/vendor/`, loaded on demand) and downloads it. It is an exact one-page copy of the client's template (Mathias, 12 Nov 2026): their letterhead image `app/report/letterhead.png` (extracted from their PDF, includes the header bar and the DYNAMIC logo; no Brand Butlers or Apple logo), positions/sizes measured from their PDF (Helvetica 8.37/11.16 pt, 0.8 pt boxes, rows grow 10.5 pt per line, centred cell text offset -1.85 pt, fixed lines at their exact x positions), their wording kept as-is (including "Where there any electrical…"). Fields: WO = ticket, City, Country, Apple ID, Store Name, Completion Date, the 9 rows from `appleRows`, Notes, lead installer + store manager names and signatures. Photos are NOT in that PDF: they are a separate "Photo report" PDF (`buildPdf(j, 'photos')` → `photoAppendix`, file `<WO>-Report.pdf`), an exact copy of the client's photo report (Mathias, 18 Nov 2026): A4 landscape, title left (14 pt bold), "Apple ID: <id> <COUNTRY>" right, their gradient bar `app/report/photo-bar.png`, two photos per page in 213.75 × 380 pt boxes, footer "Reactive Maintenance Report – Dynamic Resources" (9 pt bold) and their Apple logo `app/report/apple-logo.png` bottom right (both images extracted from their PDF). One "BEFORE & AFTER Photos" page per angle with "Before"/"After" captions, then extra photos and disposal photos two per page as "AFTER OVERVIEW Photos" (no captions). Nothing else is added. Mathias's client wants the two exported separately, never one combined file. Exports (`exportButtons`) are available as soon as a report is submitted: in the report view, after approving, and under Approvals → Approved (Export button → sheet). "Export pictures only" / the Pictures button saves the report's photos one by one (`reportPhotos`, `dlPhotos`): separate downloads on a computer, the share sheet (Save images) on phones and iPads. Names like `WO1733363_1a_Before_Front-full-fixture.jpg`. "Export videos only" / the Videos button does the same for the report's extra videos (`reportVideos`, `dlVideos`, `WO1733363_Video_1.mp4`). Installer report order (Mathias, 20 Nov 2026; `reportFlow`, `STEPS`): step 1 the 4 before photos (+ tools to bring); step 2 all questions (`report.apple`, `ynQ`), store manager, parts replaced, notes, problem, then both signatures (`setupSig` runs on step 2; Continue only when `reportMissing(j, 'answers')` is empty); step 3 the 4 after photos with the before photo alongside (`shotCards`), then one photo card per part ticked as replaced in step 2 (`replacedParts`, `report.partPhotos` = {partKey: [{k}]}, `data-pphoto`, viewer sheet `pph`, at least one photo per part required), extra photos/videos, Submit. Part photos also go in the picture export (`WO…_Part_<name>_1.jpg`), the approval view and the photo report's AFTER OVERVIEW pages, disposal photos in `report.disposal`, installer signature `instSigned` (`<job>/installer-signature.png`). Stores have `apple_id` and `city` (set on the ticket form). Migration `apple_export`; `job_submit` requires both signatures.
- Rollback: revert the last merge on `main`, push, dispatch.

## Server (Supabase)
- Project `brand-butlers` (ref `gipkzcpaqlyiqawgunhu`, region eu-north-1), used by the test version. Connected through the Supabase connector.
- Tables: profiles (who may sign in, roles, status invited/reset/active/removed), stores, jobs, reports (draft data as JSON), templates (fixture templates: name, tools, parts) and tools (the shared tools list). Templates and tools are made by admins in New ticket and shared by all admins; there are no built-in ones. Private storage bucket `photos`, one folder per job (50 MB, JPEG/PNG and video since migration `report_extras`). Installers can add any number of extra photos and videos to a report before submitting (`report.extras` = [{k, kind, poster, dur}], `extrasBlock`, `addExtras`); admins see them in the approval view. Installers can take back their own submitted report to edit it until an admin handles it (`job_reopen`: waiting → progress, report back to draft, `jobs.reopened_at`; admins see "Installer is editing"; approve/ask-for-changes only update jobs still `waiting`). `jobs.sent_back` counts send-backs (trigger) for Insights. Migration `installer_reopen`. During photos and sign-off a floating "Instructions" button reopens the ticket's video instructions.
- Row level security: admins see everything; installers only reach their jobs through `my_jobs()` (their share, never the price) and the `job_*` functions. Check with `get_advisors` after schema changes.
- Video library: table `videos` + private bucket `videos` (`<id>/video.<ext>`, `<id>/poster.jpg`, max 50 MB). Admins upload under Manage → Videos and assign videos to templates and tickets (`video_ids`). Installers get them via `my_jobs()` / `my_videos()`; the button is always called "Video instructions". Migration `video_library`. The library also holds pictures (`videos.kind` = 'video' | 'image'; pictures stored as `<id>/image.jpg` + `<id>/poster.jpg`, resized in the browser). Uploads accept several files at once. Migration `library_pictures`. Pictures can be cropped and rotated (picture editor, `PE`): the original stays at `videos.edit.orig`, the cropped copy becomes `path`/`poster` (`<id>/edited-<ts>.jpg`).
- Video editing is non-destructive: `videos.edit` (jsonb: segments, texts, fadeIn/fadeOut/fadeBetween, volume 0–2, muted, speed) is applied on playback by `makePlayer`; the original file is never changed. Auto edit samples frames (`analyzeMotion`) and keeps the parts with movement; step texts come from the video's notes. Migration `video_edits`.
- Ticket prices: the admin types two amounts per ticket (installer, admin); either may be 0 (empty = 0); the ticket price is their sum (`jobs.inst_amt`, `adm_amt`, `price`; migration `manual_amounts`). Brand Butlers is removed from all income (Mathias, 19 Nov 2026): new tickets save `bb_amt` 0, and `toJob` sets `j.price` to installer + admin for every ticket (the stored price is kept as `j.gross`), so Insights, pipeline and "Where the money goes" never include a Brand Butlers share. Use `amounts(j)` for any split (older tickets fall back to price × `inst_pct`/`adm_pct`, which are still written for compatibility). Two installers split the installer amount. `my_jobs()` gives installers only their own amount.
- All amounts are in Danish kroner (DKK) for every country. Insights shows "Revenue not approved yet" (`pipeline`: all non-approved tickets, any date, split waiting / in progress / planned) and "Where the money goes" (`moneySplit`: installers / admin / Brand Butlers, approved in the period next to to be approved, any date).
- Ticket times are always 24-hour (00:00–23:59). Scheduling is `scheduleBlock`, kept small (Mathias, 19 Nov 2026: "too big", then "half the size, enlarge when pressed"): collapsed it is one `pf` card (date · time, "In N days · free / other visits", Change); tapping it (`schToggle`, `d.schOpen`) opens inside the card a week row (Mon–Sun, ‹ › by week, dot = already booked, calendar icon = any date via a transparent date input + `showPicker`), a row of hour chips 07–18 (dot = busy) next to exact hour:minute selects, and one footer line (free that day, or the installer's other visits as small chips, orange when within 90 min). Actions `schDay`/`schWeek`/`schTime`. On PC (Mathias, 19 Nov 2026): Store and Installer side by side, same height and level (`.ntc.pair`, store tags under the address, "Edit details" link bottom right), and the When card full width underneath (`newDesk`). The support contact is not shown on the ticket form or summary. Order: ticket no. | country, store | installer, When (full), tools | parts, videos | note, Fixture template + Save as template (full, just above the price), price. Side-by-side cards are always `.pair` (same height, level) — Mathias wants matching sizes and alignment kept everywhere going forward. Don't use `<input type="time">` (it shows AM/PM on US-locale phones). Don't reuse the class `.snav` (it is the sidebar nav).
- Stores and parts (migration `stores_parts_catalog`): stores have `program` next to `apple_id`/`city`; table `parts_catalog` (name, category) is the shared parts list; `jobs.part_items` = [{name, qty}] (older tickets fall back to `parts`, qty 1). Manage has four sections (`MANAGE`: People, Stores, Parts & tools, Videos & pictures; sub-menu under Manage in the sidebar). All four use `manageHead` (section switch + main button at a fixed spot top right, 168 px wide; "Import a list" link right under it on Stores and Parts). Stores page filters: search, country chips and a program dropdown (`S.stP`, `data-setk`). The real store list (347 stores from Apple's EMEIA Programs sheet, Mathias 18 Nov 2026) is loaded in the test project. Stores page: search, country chips, table on PC, import a pasted list (`parseStoreList`: tab/semicolon/comma; Country, Store, Address, City, Apple ID, Program, or any order with a header row; optional "Replace all current stores"). Parts page: catalogue by category, import (`parsePartList`, "Category;Part"), tools list. Ticket form: Store, Installer, Tools, Parts and Video instructions all use the same field card `pf()` (icon tile, title/sub, Change/Choose pill, selected items as rows below with × or a stepper) and open a searchable sheet: `pickstore`, `pickinst` (`instPickList`, availability that day, lead or second via `U.im`), `picktools` (`toolPickList`, type a new tool + Enter adds it to the shared list), `pickparts` (`partPickList`, quantities), `pickvideos`. Keep new ticket-form fields in this pattern; installers see tools and parts on the job card and in report step 1 and can add parts they replaced on site from the same picker.
- Light/dark mode: Light | Dark switch at the bottom of the PC sidebar, above Installer view (`setTheme`, `applyTheme`, `localStorage` `bb.theme`, sets `data-theme` on <html>; follows the device until someone picks). Colours come from the `:root` tokens, which already have dark values.
- PC layout fills the screen: `body.desk .app` has no max width (sidebar 248 px + content).
- Installers are only offered for the countries in their profile (`installers(c)` filters on `u.cs`; changing the ticket's country clears an installer who doesn't belong there).
- Accounts can cover several countries: `profiles.countries` (home country `country` first; migration `multi_country`), set under Manage → person (Countries list, "Make home"). In the app `u.cs`; region value 5 = "Mine" (all of the admin's countries, default view when they have more than one) next to 0–3 and 4 = Nordic; use `regionCs`/`inR`/`regionName` for any country filter. All admins can still see every country (no access limits by country).
- Sign-in is email + password only (Mathias decided against Sign in with Apple on 3 Nov 2026). Admins add the email first; the person then creates a password and confirms name and country.
- Edge functions: `account` (claim = first password / after reset, with name + country; only accepts a SHA-256 hash) and `admin` (add, update, reset, remove people; admins only; removing erases the phone number). Both allow only the app's own origin.
- Trigger `guard_new_login` on auth.users: only emails in active profiles can get a login.
- The schema and functions are the migrations `core_schema`, `functions_storage_seed`, `apple_sign_in` (now only the login guard and account_status with country), `templates_and_tools`, `video_library`, `video_edits`, `library_pictures`, `report_extras`, `installer_reopen`, `apple_export`, `privacy_by_design` (account_status returns only status; `admin_names` dropped), `multi_country`, `manual_amounts`, `stores_parts_catalog` and `orphan_photo_cleanup` (`orphan_photo_files()`: files in `photos` whose ticket no longer exists; the app removes them via the Storage API when an admin signs in, `cleanOrphans`) in the project; read them with `list_migrations` / `get_edge_function` before changing anything.

## Notifications (Mathias, 24 Nov 2026; migration `notifications_push`)
- Table `notifications` (own rows only via RLS) is filled by database triggers: `notify_dynamic` (statement trigger on `dynamic_tickets` insert → one message per active admin, "N new tickets from Dynamic") and `notify_assign` (jobs insert / installer or second changed → the installer(s), not the admin who made the change).
- Each new row is pushed by `pg_net` → edge function `push` (verify_jwt off; it only sends rows not yet pushed, `pushed_at`), web push with `npm:web-push`. VAPID public key is `VAPID_PUBLIC` in the app; the private key is in Supabase Vault (`vapid_private`), read only by `push_config()` (service role). Devices: table `push_subs`.
- App: bell in the header and "Notifications" in the PC sidebar (unread count), sheet `notes` with "Turn on notifications" (`pushOn`, `sw.js` push handler; iPhone needs Add to Home Screen first). Opening the sheet marks them read; tapping one opens the Dynamic list or the job (`openNote`).
- Photo slots offer "Take … photo" (camera) and "From library" (no `capture`), Retake also has From library; step 1 has the extra photos/videos block too.
